# Semantic Evaluation with Sindi — Frontier-model Invariant Fill

Semantic comparison of the invariants generated by the frontier model (`gpt:gpt-4o`) against the ground-truth predicates extracted from each contract's `diff.diff`, using **Sindi** (Semantic Invariant Differencing for Solidity).

## Method

Each generated predicate is compared to its ground truth by invoking Sindi's own CLI unchanged:

```
python main.py compare "<generated>" "<ground_truth>"
```

Argument order is `compare(generated, ground_truth)`, so in Sindi's verdicts the *first predicate* is the model's output and the *second predicate* is the ground truth. When Sindi raises a parsing error, the raw error is stored in a separate column and the verdict is left empty.

Sindi returns one of four verdicts:

- `The predicates are equivalent.` — semantic match (even if syntactically different)
- `The first predicate is stronger.` — the generated invariant is **stronger** than the patch (over-constrained)
- `The second predicate is stronger.` — the ground truth is stronger, i.e. the generated invariant is **weaker** than the patch (under-constrained)
- `The predicates are not equivalent and neither is stronger.` — no logical relation

### Syntactic vs. semantic

The syntactic exact-match (FLAMES rules) counted **10/30**. Sindi's semantic comparison additionally recognises **1** reordered-but-equivalent case that the syntactic matcher missed:

- `202404_HoppyFrogERC`: GT `swapAmount <= maxSwapForSell` ≡ generated `maxSwapForSell >= swapAmount`

(Nimbus was a syntactic match but yields a Sindi parse error on `**`, so it does not appear as a Sindi `equivalent`; see limitations.)

### How the model fails when it fails

Beyond a binary right/wrong, Sindi's strength relation shows *how* wrong the misses are:

- **2 cases** where the ground truth is strictly stronger — the model produced a **weaker** invariant that would not block all the attacks the patch blocks (e.g. `202409_OnyxDAO`: GT `repayAmount == borrowedAmount` vs generated `borrowedAmount <= repayAmount`, which also admits under-repayment).
- **1 case** where the generated invariant is strictly stronger — over-constrained (`202202_TecraSpace`: generated adds `_balances[from] >= amount` on top of the GT allowance check).
- **14 cases** with no logical relation — genuinely different predicates.

## Limitations (Sindi parse errors)

Two predicates could not be parsed by Sindi's tokenizer - the generated predicate is left unjudged, not counted as a miss:

| Contract | Line | Sindi error |
|---|---|---|
| 202109_Nimbus | 405 | `Error: Unexpected token MULTIPLY at position 21` |
| 202406_WIFCOIN_ETH | 979 | `Error: Expected token RPAREN but got DOT at position 20` |

- **Nimbus** fails on the exponent operator `**` combined with a digit-underscore literal (`10_000**2`); note GT and generated differ only by the underscore, so this is effectively an equivalent pair the tokenizer cannot process.
- **WIFCOIN_ETH** fails on chained method-call structure in the generated predicate.

One further row (`202603_AlkemiEarn`) has no generated predicate at all — the model hit the API token-per-request limit on that (very large) contract — so there is nothing to compare.

## Comparison: GPT-4o vs FLAMES-CodeLlama (per-contract, n=28)

To compare the two models on equal footing, results are collapsed to the
**contract level**: a contract counts as a match if **at least one** of its holes
is judged `equivalent` by Sindi. This removes the extra holes GPT produces for
multi-`require` contracts (Anyswap, Uwerx, pSeudoEth) and the extra holes Llama
produces (Uwerx, pSeudoEth, grok), so both models are scored over the **same 28
contracts**. Both runs use the same ground truth per contract.

| Metric (per contract, n=28) | FLAMES-CodeLlama | GPT-4o |
|---|---|---|
| Semantically equivalent (Sindi) | **2/28 (7.1%)** | **10/28 (35.7%)** |

### The two models do not solve the same contracts

The headline gap (35.7% vs 7.1%) hides that the overlap is small:

- Solved by **both**: 1/28 — `202206_InverseFinance`.
- Solved by **GPT only**: 9 — Opyn, Anyswap, N00d, JAY, VINU, uniclyNFT, pSeudoEth, HoppyFrog, JokInTheBox.
- Solved by **Llama only**: 1 — `202406_APEMAGA` (GT `msg.sender == account`; Llama reproduced it exactly, GPT generated the non-equivalent `_owner == account`).

So GPT does not strictly dominate: there is one contract the smaller fine-tuned
model recovers and the frontier model does not.
